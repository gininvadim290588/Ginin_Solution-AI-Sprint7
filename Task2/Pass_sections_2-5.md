# Паспорт AI-инициатив — разделы 2–5

## Инициатива 1. Приоритизация подозрительных операций для ручной проверки

### Раздел 2. Постановка

| Поле | Решение
|---|---|
| Бизнес-действие | Меняем порядок ручной проверки: в первую очередь сотрудник проверяет операции, которые система считает наиболее важными. Обязательные AML-проверки при этом сохраняются. |
| Объект и единица решения | Решение принимается для отдельной операции. При этом учитывается информация о клиенте, контрагенте и история операций за определённый период. |
| Момент | Ранжирование выполняется после поступления операции. В пилоте используем пакетную обработку (batch). В production можно перейти на batch или почти онлайн-обработку (near-real-time), если это потребуется бизнесу. |
| Операция | Система определяет порядок проверки операций — какие проверить раньше. Она не выносит окончательный вердикт «подозрительная / не подозрительная». |
| Модальность | Основная информация — числовые и временные признаки, а также связи между клиентами, контрагентами и счетами. Текст назначения платежа используется как дополнительный источник информации. |
| Выход модели | Модель возвращает оценку приоритета `review_priority_score`, место операции в очереди (`rank`) и причины, которые повлияли на приоритет. |
| Бизнес-выход | Формируется очередь операций для ручной проверки в порядке их приоритета. |
| Источник правильного ответа | Основой являются результаты проверки сотрудниками. Дополнительно регулярно проверяется случайная или специально сформированная контрольная выборка операций. Исторические расследования и подтверждённые случаи можно использовать как дополнительные данные (weak labels), но не считать их полностью достоверной разметкой (gold labels). |
| Конвейер | Получение операции (детерминированное)→ Обязательные правила и AML-сигналы (детерминированное)→ Enrichment (детерминированное)→ Расчёт признаков / Features (детерминированное)→ Ranking / ML-модель (обучаемое)→ Объединение с обязательной очередью (детерминированное)→ Формирование очереди (детерминированное)→ Ручная проверка сотрудником (человек)→ Сохранение результата проверки (детерминированное |
| Альтернативные варианты | Классификацию «подозрительная / не подозрительная» пока не используем, так как для неё нужно накопить достаточно качественной разметки. Anomaly detection можно использовать как дополнительную модель для сравнения. Для пилота выбран подход с ранжированием операций (ranking). |

### Раздел 3. Оценка качества

| Поле | Решение |
|---|---|
| **Бизнес-метрика**| Доля полезных для углублённой проверки операций при фиксированной мощности сотрудников; guardrail — отсутствие роста необоснованных приостановок. |
| Положительный класс | Операция, которую эксперт по гайдлайну относит к требующей углублённой проверки. Формально подтверждённые случаи — отдельный строгий слой. |
|**Метрика под решение** | Recall@K при K около 10 000 проверок/месяц. В нашем случае сотрудник не может проверить весь поток операций. Есть ограничение — примерно 10 000 проверок в месяц. Поэтому ML-модель должна выбрать из большого потока именно те операции, которые стоит проверить в первую очередь.; дополнительно Precision@K - Какая доля операций из первых K действительно оказалась подозрительной?, lift - Насколько лучше модель находит подозрительные операции по сравнению со случайным выбором? и recall по сценариям - Не теряем ли мы важные типы подозрительных операций?|
| **Baseline** | Текущий способ работы: сначала применяются действующие правила, внешние AML-сигналы и текущая логика, по которой операции отправляются на проверку. С ним сравниваем результат новой ML-модели. |
| **Проверочная выборка** | Используем две группы данных: отложенные данные с экспертной разметкой и независимую случайную контрольную выборку из операций, которые обычно не попадают на ручную проверку. Это позволяет оценить качество модели не только на уже известных случаях. |
| **Рабочая точка** | Берём столько операций из начала рейтинга, сколько сотрудники реально могут проверить за месяц — около 10 000 операций. Именно на этом объёме оцениваем работу модели. |
| **Порог** | Порог для принятия решения заранее не задаём. Сначала измеряем текущий результат (baseline) и оцениваем стоимость ошибок, после чего выбираем подходящий порог. Публичные benchmark-значения не используем как готовый порог. |
| **Цена ошибок** | Если модель пропустила подозрительную операцию, возникает регуляторный и финансовый риск. Если модель дала слишком высокий приоритет нормальной операции, сотрудник потратит на неё время, а обслуживание клиента потенциально может замедлиться. |
| **Guardrails** | Защитные ограничения, которые не позволяют ML-модели нарушить обязательные AML-процедуры. Модель не принимает юридическое решение, не должна увеличивать количество необоснованных приостановок, все действия записываются в журнал, а признаки не должны использовать информацию из будущего (future leakage). |

### Раздел 4. Готовность данных

| Поле | Решение|
|---|---|
| **Решение** | Система помогает определить, какие операции сотруднику финансового мониторинга нужно проверить в первую очередь. |
| **Объект и детализация** | Основной объект — отдельная операция. При оценке также учитываем клиента, счёт, контрагента и историю его операций за определённый период. |
| **Источники данных и владелец** | Используем данные транзакционных систем, справочников, результаты AML-проверок и внешние сигналы. За данные отвечает финансовый мониторинг совместно с владельцами соответствующих систем. |
| **Откуда берём правильный ответ** | Используем результаты проверок сотрудников и независимую случайную контрольную выборку операций. |
| **Доступность признаков в production** | Для каждого признака проверяем, что его действительно можно получить в production в момент принятия решения. Используем только информацию, которая была доступна на этот момент. |
| **Разметка данных** | Сотрудники финансового мониторинга размечают операции по единому гайдлайну. Часть операций проверяется двумя сотрудниками, чтобы убедиться, что правила разметки понимаются одинаково. |
| **Смещение выборки** | Оно высокое: раньше сотрудники в основном проверяли операции, которые уже были отобраны правилами или внешними сигналами. Поэтому операции, которые никто не проверял, нельзя автоматически считать нормальными. |
| **Репрезентативность данных** | Контрольная выборка должна содержать разные типы клиентов и операций, разные суммы и каналы, основные AML-сценарии, а также редкие, но потенциально дорогостоящие случаи. |
| **Объём данных** | В месяц проходит около 20–25 млн операций. Из них примерно 35 тыс. получают сигналы, около 10 тыс. проходят ручную проверку и около 400 — углублённое расследование. Подтверждённых подозрительных случаев очень мало — единицы. |
| **Качество данных** | Данные из разных систем могут иметь разный смысл и формат. Результаты расследований могут появляться с задержкой, а разные источники могут противоречить друг другу. Поэтому нужно отслеживать происхождение данных (lineage) и не допускать использования информации из будущего (data leakage). |
| **Право на использование данных** | В данных могут содержаться персональные данные и банковская тайна. Поэтому до использования данных необходимо подтвердить правовые основания, цели использования, правила передачи и хранения с комплаенсом, DPO и юристами. |
| **Итоговая оценка** | **Есть пробел, но пилот возможен.** Для ranking-пилота данных достаточно, однако пока нет большой качественной и независимой разметки, которая позволила бы надёжно обучить обычную supervised-модель классификации. |

### Раздел 5. Карточка эксперимента

| Поле | Решение |
|---|---|
| Где именно теряем | В непроверяемой части потока из-за selection bias; дополнительно — в редких подтверждённых случаях и задержке labels. |
| Гипотеза причины | Правила формируют пул кандидатов, но не оптимально ранжируют его относительно ограниченной мощности экспертов. |
| Конкурирующие объяснения | Bottleneck — мощность сотрудников; низкая согласованность labels; эффект исчезнет после корректной контрольной выборки. |
| Рычаг | Sampling → признаки → ranking → top-K → post-processing. |
| Дешёвый различающий эксперимент | Blind-разметка независимой вероятностной контрольной выборки и сравнение текущего порядка с ranking-кандидатами при одинаковом K. |
| Ожидаемый эффект | Рост Recall@K/lift относительно baseline без ухудшения guardrails. |
| Стоимость проверки | Экспертные часы + data engineering + ML engineering; N определяется power analysis. |
| Критерий остановки | Нет практически значимого lift при достаточном N либо нарушены guardrails. |

## Инициатива 2. Распознавание и оцифровка документов кредитной заявки

### Раздел 2. Постановка

| Поле | Решение |
|---|---|
| Бизнес-действие | Сократить ручной перенос данных из PDF, сканов и фотографий в кредитную заявку. |
| Объект и единица решения | Документ/страница и извлекаемые поля. |
| Момент | При загрузке документа; pilot — асинхронно. |
| Операция | OCR + классификация документа + извлечение полей. |
| Модальность | PDF, скан, фото, изображение, текст. |
| Выход модели | Тип документа, поля, confidence, координаты/источник. |
| Бизнес-выход | Заполненные поля + подсветка источника; low-confidence и критичные поля — human review. |
| Источник правильного ответа | Значения, подтверждённые сотрудником; критичные поля — gold set. |
| Конвейер | Upload → quality check → OCR → classification → extraction → normalization/rules → threshold → human review. |
| Альтернативные постановки | Полная автоматизация без контроля не является целью пилота. |

### Раздел 3. Оценка качества

| Поле | Решение |
|---|---|
| Бизнес-метрика | Сокращение времени обработки без роста критических ошибок. |
| Положительный класс | Корректно извлечённое и нормализованное поле; для classification — корректный тип документа. |
| Метрика под решение | Exact/normalized field match, classification F1/accuracy; CER как диагностическая метрика; бизнесовая — доля полей без ручной корректировки и время. |
| Baseline | Полностью ручной перенос и проверка. |
| Проверочная выборка | Holdout по типам документов, источникам, качеству, шаблонам и редким форматам. |
| Рабочая точка | Автопринятие только выше threshold; критичные поля при недостаточной уверенности — human review. |
| Порог | Определяется по стоимости ошибки и результатам пилота, а не произвольным benchmark. |
| Цена ошибок | Ошибка в критичном поле может повлиять на кредитный анализ; ложная отправка на проверку стоит времени. |
| Guardrails | Provenance, контроль критичных полей, отсутствие роста underwriting errors. |

### Раздел 4. Готовность данных

| Поле | Решение |
|---|---|
| Решение | OCR и извлечение структурированных данных из документов кредитной заявки. |
| Объект и гранулярность | Документ, страница, поле. |
| Источник и владелец | Документы кредитного процесса; владелец — кредитный/underwriting-контур. |
| Источник правильного ответа | Проверенные сотрудниками значения + структурированные поля заявки как дополнительная сверка. |
| Доступность признаков в проде | Документ доступен при загрузке; будущие признаки исключаются. |
| Разметка | Типы документов и поля проверяются сотрудниками; часть набора — двойная разметка. |
| Смещение отбора | Возможен перекос в сторону типовых документов; нужны редкие шаблоны и плохие сканы. |
| Репрезентативность | Тип документа, источник, качество, шаблон, формат, редкие случаи. |
| Объём | Документы есть, но объём по типам и критичным полям в кейсе не задан; требуется sizing pilot. |
| Качество | Форматы неоднородны: Excel, PDF, сканы, выгрузки и фотографии. |
| Право использовать | ПДн и финансовые сведения: правовое основание и границы хранения/передачи подтверждаются комплаенсом/DPO/юристами. |
| Вердикт | **Можно начинать пилот** при подтверждении legal contour и representative gold set. |

### Раздел 5. Карточка эксперимента

| Поле | Решение |
|---|---|
| Где именно теряем | Низкое качество изображения, редкие шаблоны, сложные поля, normalization после OCR. |
| Гипотеза причины | Основной эффект даст автоматизация переноса, а не полная автоматизация кредитного решения. |
| Конкурирующие объяснения | Задержка вызвана проверкой, а не вводом; редкие форматы съедят эффект. |
| Рычаг | Data quality, OCR, classifier, extraction, rules, threshold. |
| Дешёвый различающий эксперимент | Representative sample: ручной процесс против extraction + human verification, с разрезом по качеству. |
| Ожидаемый эффект | Снижение времени ввода при сохранении точности критичных полей. |
| Стоимость проверки | Gold set + разметка + ML/data engineering. |
| Критерий остановки | Нет достаточной экономии времени или критические ошибки выше допустимого уровня. |

## Инициатива 18. Извлечение финансовых показателей

### Раздел 2. Постановка

| Поле | Решение |
|---|---|
| Бизнес-действие | Автоматически формировать нормализованный financial profile для кредитного анализа. |
| Объект и единица решения | Показатель внутри документа/выписки с периодом, единицей и источником. |
| Момент | При загрузке пакета документов; pilot — batch/asynchronous. |
| Операция | Извлечение + нормализация + валидация. |
| Модальность | PDF, сканы, Excel/экспорты, выписки, неструктурированный текст/таблицы. |
| Выход модели | `{metric, value, period, unit, source_location, confidence}`. |
| Бизнес-выход | Нормализованный financial profile + флаги противоречий; критичные значения подтверждаются сотрудником. |
| Источник правильного ответа | Проверенные человеком значения + структурированные данные при наличии. |
| Конвейер | Ingestion → classification/layout → extraction → normalization → consistency checks → threshold → human review. |
| Альтернативные постановки | MVP по ограниченному набору критичных показателей вместо извлечения всего отчёта. |

### Раздел 3. Оценка качества

| Поле | Решение |
|---|---|
| Бизнес-метрика | Сокращение времени подготовки financial profile без роста ошибок в критичных показателях. |
| Положительный класс | Верно извлечённый, нормализованный показатель с правильным периодом, единицей и знаком. |
| Метрика под решение | Normalized exact match, completeness, provenance completeness, доля без ручной корректировки. |
| Baseline | Ручное извлечение и проверка. |
| Проверочная выборка | Holdout по источнику, формату, качеству, типу отчётности, редким форматам и конфликтам. |
| Рабочая точка | Автопринятие только выше threshold; критичные/конфликтные значения — human review. |
| Порог | Определяется стоимостью ошибки и пилотными результатами; внешний benchmark не используется как критерий сам по себе. |
| Цена ошибок | Ошибка в ключевом финансовом показателе искажает кредитный анализ; ручная проверка имеет стоимость времени. |
| Guardrails | Provenance, контроль единиц/периодов/знаков, арифметические проверки, human review. |

### Раздел 4. Готовность данных

| Поле | Решение |
|---|---|
| Решение | Извлечение и нормализация финансовых показателей. |
| Объект и гранулярность | Показатель × документ × период. |
| Источник и владелец | Бухгалтерские документы и банковские выписки кредитного процесса; владелец — кредитный/underwriting-контур и владельцы источников. |
| Источник правильного ответа | Проверенные человеком значения + структурированные данные при наличии. |
| Доступность признаков в проде | Документы доступны при подготовке заявки; признаки будущего решения исключаются. |
| Разметка | Gold set показателей с координатой/источником; двойная проверка части набора. |
| Смещение отбора | Возможна пере представленность типовых отчётов клиентов, дошедших до поздних стадий underwriting. |
| Репрезентативность | Форматы, периоды, источники, качество, редкие типы и конфликтующие значения. |
| Объём | Данные есть, но точный объём по форматам и важным показателям в кейсе не задан; нужен inventory. |
| Качество | Неоднородные форматы, разные единицы, знаки, названия и периодизация. |
| Право использовать | ПДн/финансовые сведения: legal basis и границы обработки подтверждаются комплаенсом/DPO/юристами. |
| Вердикт | **Разрыв с планом закрытия**: до пилота нужны MVP-показатели, representative sample и gold set. |

### Раздел 5. Карточка эксперимента

| Поле | Решение |
|---|---|
| Где именно теряем | Сопоставление названий, сложные таблицы, единицы/периоды, редкие форматы. |
| Гипотеза причины | Основные трудозатраты — поиск и перенос; ML extraction + deterministic checks удержат качество. |
| Конкурирующие объяснения | Bottleneck — сверка противоречий; ручная проверка всё равно нужна большинству документов; эффект ограничен малым числом показателей. |
| Рычаг | MVP-показатели, layout-aware extraction, normalization, arithmetic checks, threshold/human review. |
| Дешёвый различающий эксперимент | Representative sample: manual против extraction + validation по времени, critical-field accuracy и доле без исправлений. |
