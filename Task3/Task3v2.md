## 1. Инициатива №1 — автоматическое выявление подозрительных операций

### 1.1. Архитектурное решение

В рамках пилота AI-сервис не принимает решение о признании операции подозрительной. Его задача — рассчитывать приоритет операции для ручной проверки сотрудником финансового мониторинга.

Цепочка обработки:

Операция

   ↓
   
Формирование snapshot данных

   ↓
   
Расчёт признаков

   ↓
   
ML-модель

   ↓
   
Калибровка score

   ↓
   
Порог / зона abstention

   ↓
   
Формирование причин

   ↓
   
Техническая валидация результата

   ↓
   
Обязательные AML-правила

   ↓
   
Очередь проверки

   ↓
   
Сотрудник финансового мониторинга

   ↓
   
Результат проверки / label

Ключевой принцип:

ML отвечает только за обучаемую часть — оценку приоритета. Детерминированная логика отвечает за обязательные правила, контроль качества данных, валидацию и fallback. Финальное решение остаётся за сотрудником.

  "decision_time": "2026-09-22T10:15:30Z",

  "priority_score": 0.0,
  "rank": 123,

  "reasons": [

    "name": "aml-review-ranking",

- "source_refs";
- "status";

## 5. Валидация перед бизнес-действием

До попадания результата в очередь выполняются следующие проверки:

1. Проверка JSON/schema.
2. Проверка "operation_id".
3. Проверка времени принятия решения.
4. Проверка версии модели.
5. Проверка "feature_snapshot_id".
6. Проверка диапазона "priority_score".
7. Проверка существования источников данных.
8. Проверка актуальности признаков.
9. Проверка полноты признаков.
10. Выполнение обязательных AML-правил.
11. Проверка конфликта ML-рекомендации с обязательными правилами.
12. При критической ошибке — переход в "FALLBACK" или "RULE_ONLY".

Только после прохождения проверок результат может попасть в очередь ручной проверки.

««операция является подозрительной».»

## 7. Режим обработки

Основной режим — асинхронный.

Transaction

    ↓
    
Ingestion

    ↓
    
Feature calculation

    ↓
    
ML scoring

    ↓
    
Validation

    ↓
    
Review Queue

Почему асинхронно

Асинхронная обработка:

- не блокирует транзакционную систему;
- позволяет повторять обработку;
- позволяет масштабировать scoring независимо;
- позволяет использовать batch processing;
- естественно интегрируется с ручной очередью.

Идемпотентность

Повторный запуск не должен создавать несколько одинаковых записей.

Идемпотентность можно обеспечить ключом:

(operation_id,
 feature_snapshot_id,
 model_version)

## 8. Batch-обработка

Для повторного расчёта исторических операций используется batch.

Например:

DWH

 ↓
 
Feature Builder

 ↓
 
Ranking Model

 ↓
 
Evaluation

Batch используется для:

- переоценки исторических данных;
- анализа drift;
- тестирования новой модели;
- offline evaluation;
- формирования контрольных выборок.

---

## 9. Fallback

Fallback должен срабатывать не только при технической ошибке.

Триггеры fallback

Ситуация| Действие
|---|---|
Отсутствует обязательный признак| Fallback
Признак устарел| Fallback
Недостаточно истории клиента| Fallback / ограниченный режим
Значения вне допустимого диапазона| Fallback
Out-of-distribution| Abstention
Модель попала в abstention zone| Ручная проверка
ML конфликтует с обязательным правилом| Приоритет правила
Feature Service недоступен| Rule-only / fallback
ML Service недоступен| Rule-only / fallback
Таймаут внешнего источника| Не считать операцию автоматически чистой
Некорректная schema| Fallback
Отсутствует source reference| Fallback

Ключевой принцип

«Ошибка AI ≠ операция чистая»

Если AI-сервис недоступен, операция должна продолжить обрабатываться существующим обязательным AML-контуром.

## 10. Мониторинг

Мониторинг разделяется на четыре уровня.

### 10.1. Input monitoring

Контролируются:

- объём входных операций;
- доля пропущенных данных;
- freshness;
- изменение распределения признаков;
- schema drift;
- изменение количества операций по сегментам.

### 10.2. Model monitoring

Контролируются:

- распределение "priority_score";
- доля "abstention";
- изменение распределения score;
- drift признаков;
- calibration;
- стабильность модели;
- Recall@K;
- Precision@K;
- Lift.

Метрики качества рассчитываются на контрольной выборке с экспертной разметкой.

### 10.3. Queue monitoring

Контролируются:

- размер очереди;
- возраст самой старой операции;
- среднее время ожидания;
- скорость обработки;
- количество операций на сотрудника;
- доля операций, попавших в fallback.

### 10.4. Human monitoring

Контролируются:

- время ручной проверки;
- доля согласия/несогласия с рекомендацией модели;
- распределение labels;
- количество повторных проверок;
- доля операций, по которым модель систематически ошибается.

---

## 11. Business monitoring

Основные бизнес-метрики:

- Recall@K;
- Precision@K;
- Lift относительно текущих правил;
- Recall по отдельным сценариям;
- количество операций, попавших в ручную проверку;
- средняя нагрузка сотрудника;
- доля необоснованных приостановок;
- количество клиентских жалоб.

При этом качество модели оценивается отдельно от эффективности процесса.

---

## 12. Триггеры пересмотра модели

Пересмотр или rollback выполняется при:

- существенном ухудшении качества на контрольной выборке;
- росте abstention;
- существенном drift;
- изменении бизнес-процесса;
- изменении состава операций;
- изменении обязательных AML-правил;
- изменении доступности или качества источников;
- изменении нагрузки на сотрудников.

При критическом ухудшении используется предыдущая версия модели или deterministic rule-based fallback.

## 14. Архитектурный принцип инициативы №2

ML используется для:

- OCR;
- классификации документа;
- извлечения полей.

Детерминированная логика используется для:

- проверки формата;
- обязательности полей;
- проверки диапазонов;
- проверки согласованности;
- проверки арифметики;
- маршрутизации низкоуверенных результатов.

Человек проверяет:

- критические поля;
- низкую уверенность;
- противоречивые документы;
- документы, которые система не смогла классифицировать.

## 16. Fallback инициативы №2

Fallback используется при:

- невозможности прочитать файл;
- неизвестном типе документа;
- низком качестве изображения;
- низкой уверенности OCR;
- отсутствии обязательного поля;
- противоречии между документами;
- нарушении schema;
- отсутствии источника значения;
- документе вне обучающей выборки.

В этих случаях документ передаётся сотруднику.

## 20. Fallback инициативы №18

Fallback необходим при:

- отсутствии source reference;
- невозможности определить период;
- неоднозначной единице измерения;
- конфликте документов;
- низкой уверенности модели;
- невозможности определить показатель;
- нарушении арифметических правил;
- показателе вне известного диапазона;
- неизвестном формате документа.

Критические финансовые показатели при fallback направляются на ручную проверку.

## 21. Работа с контекстом и инструментами

Для трёх инициатив архитектура использования контекста различается.

Инициатива| Контекст| Retrieval| Tool
|---|---|---|---|
№1 AML ranking| История операций, агрегаты, контрагенты, внешние сигналы| Не требуется| Не требуется
№2 OCR документов| Сам документ, страницы, OCR-текст| Внутри документа| OCR / parser
№18 финансовые показатели| Документ, таблицы, предыдущие показатели клиента| Возможен поиск по документу / пакету| OCR / parser / table parser

Для инициатив №2 и №18 документ рассматривается как недоверенный входной контент, а не как набор инструкций для AI.

Текст документа не должен иметь возможности:

- изменить системные инструкции;
- вызвать произвольный инструмент;
- получить доступ к внутренним сервисам;
- изменить бизнес-правила;
- обойти валидацию.

## 22. Trust Boundaries и безопасность

| Boundary | Угроза | Мера защиты |
|---|---|---|
| **T1. Транзакционные системы → AI/AML** | В систему могут попасть персональные данные или банковская тайна, а при недостаточной защите они могут быть перехвачены | Защищаем соединение с помощью mTLS, проверяем права каждого сервиса и пользователя, шифруем данные, передаём только необходимые данные и записываем действия в журнал аудита |
| **T2. Внешние сигналы → AI/AML** | Внешний источник может передать поддельные или неправильные данные | Разрешаем обмен только с известными источниками, проверяем происхождение данных и их формат, а также ограничиваем права внешних систем |
| **T3. Клиентский документ → Document AI** | Загруженный файл может содержать вредоносный код или специально подготовленный текст, который пытается повлиять на работу AI | Проверяем файл на вирусы, обрабатываем его в изолированной среде (sandbox), не даём документу прямого доступа к системе и дополнительно проверяем результат AI |
| **T4. Документ → Financial Extraction** | В документе могут быть изменены или неправильно распознаны суммы и другие финансовые данные | Сохраняем ссылку на исходный документ, проверяем происхождение данных и сравниваем важные значения с другими документами или источниками |
| **T5. Model Artifact → Runtime** | Злоумышленник может подменить ML-модель перед её запуском | Подписываем файлы моделей, контролируем их версии, проверяем целостность и загружаем модели только из доверенного хранилища (registry) |
