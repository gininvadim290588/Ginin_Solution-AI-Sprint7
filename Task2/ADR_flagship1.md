# ADR-001. Приоритизация подозрительных операций для ручной проверки

**Статус:** принято для пилота, целевая архитектура предварительная  
**Дата:** 22.09.2026  
**Инициатива:** 1. Автоматически выявлять подозрительные операции по счетам

## Контекст

RetailBank обрабатывает около 20–25 млн операций в месяц. Правила и внешние сигналы формируют около 35 тыс. сигналов, около 10 тыс. операций проходят ручную проверку, около 400 — углублённое расследование. Формально подтверждённых случаев немного и они появляются с задержкой.

Историческая выборка проверок не является случайной: операции уже были отобраны правилами и внешними сигналами. Непроверенные операции нельзя считать отрицательным классом.

Поэтому исходная постановка «автоматически определить схему» уточняется до **ранжирования операций для ручной проверки**. Модель не принимает AML-решение и не отменяет обязательные процедуры.

## Жёсткие ограничения

1. ML не заменяет обязательные процедуры финансового мониторинга.
2. Модель не выдаёт юридический вердикт «схема / не схема».
3. Непроверенная операция не считается отрицательным примером.
4. Признаки должны быть доступны в момент решения; future leakage запрещён.
5. Сохраняется audit trail: версия модели, признаки, score, время и причины.
6. ПДн и банковская тайна не передаются внешнему провайдеру до legal/security approval.
7. Обязательные правила не исчезают из очереди из-за ML.
8. Пилот не должен автоматически приостанавливать операции.

## Сравнительные критерии

Сравниваются доступ к чувствительным данным, контроль модели, latency/throughput, auditability, стоимость пилота и production, переносимость, MLOps и возможность замены поставщика.

## Рассмотренные варианты

| Вариант | За | Против | Решение |
|---|---|---|---|
| Публичный API | Быстрый старт | Передача чувствительных данных, контроль хранения/обработки, vendor lock-in | **Отсечён** до отдельного legal approval |
| Выделенный контур провайдера | Изоляция, меньше MLOps | Внешняя зависимость, legal/security review | Резерв после approval |
| Self-hosting в облаке | Контроль модели/данных, масштабирование | Нужен закрытый cloud contour | **Пилот** |
| On-prem | Максимальный контроль | Более дорогой/медленный старт | **Целевой production** |
| Гибрид | Разделение data/inference | Сложнее эксплуатация | Допустим при необходимости |

## Решение

### Данные

Используются одновременно:

1. экспертная разметка операций из приоритетной очереди по единому гайдлайну;
2. постоянная вероятностная контрольная выборка из всего потока — случайная или стратифицированная по сегментам, суммам и типам операций.

Это дороже, чем обучение только на исторической очереди, но позволяет оценивать непроверяемую часть потока и контролировать selection bias.

Правила, внешние сигналы, эскалации и исходы расследований остаются weak labels/дополнительными сигналами. Эскалация не равна подтверждённой схеме; обучение только на таких labels воспроизвело бы существующую логику отбора.

### Размещение

**Пилот:** self-hosting в закрытом облачном/тестовом контуре банка, batch inference. При отсутствии допустимого cloud contour — on-prem без изменения output contract.

**Целевой production:** on-prem или self-hosted private cloud после заключения ИБ/комплаенса/DPO/юристов.

Публичный API не является базовым вариантом.

### Шортлист модели

Шортлист определяется output contract `score + rank + reasons + model_version` и сценарием top-K:

1. Gradient Boosting / Learning-to-Rank — основной кандидат для табличных и временных признаков.
2. Anomaly Detection — challenger для новых паттернов.
3. Rule-based baseline — обязательный baseline.
4. NLP-модель назначения платежа — источник дополнительного признака.
5. Supervised classifier «схема/не схема» — не основной кандидат, пока не накоплен качественный label set.

## Приёмочный набор

### Сценарии

- транзит;
- обналичивание;
- дробление;
- обычный профиль;
- разные диапазоны сумм;
- разные клиентские сегменты;
- каналы;
- редкие дорогие случаи;
- операции вне исторической очереди.

### Объём

Точный N определяется power analysis после получения baseline и согласования ожидаемого эффекта. Для пилота ориентир — несколько тысяч экспертно размеченных операций плюс постоянная контрольная выборка. Это ориентир для планирования, а не заранее объявленный статистически достаточный размер.

### Метрики и пороги

Основная — **Recall@K**, где K соответствует фактической мощности ручной проверки (около 10 тыс./месяц).

Дополнительно: Precision@K, lift, recall по сценариям, нагрузка сотрудников и guardrails.

Числовые пороги устанавливаются по baseline, доверительным интервалам и стоимости ошибок. Публичные benchmark «92% accuracy» не используются как критерий.

### Провал сценария

Провал означает недостаточное ранжирование данного типа операций. Перед сменой модели проверяются label quality, N, feature availability, leakage, drift и sampling. Если после проверки проблема сохраняется, модель не допускается к сценарию либо меняется постановка/признаки.

### Триггер смены решения

- legal/security запрет контура;
- отсутствие практически значимого lift;
- ухудшение guardrails;
- появление достаточного supervised label set;
- изменение мощности ручной проверки;
- существенный рост TCO;
- drift и потеря репрезентативности acceptance set.

## Риски и что с ними делаем

| Риск | Что это означает | Что делаем |
|---|---|---|
| Selection bias | В обучающей выборке могут оказаться не все типы операций, поэтому модель будет хуже работать на реальном потоке | Берём контрольную выборку из всего потока операций и сравниваем её с обучающей выборкой |
| Label noise | Результаты ручной проверки могут содержать ошибки или разные трактовки одного случая | Создаём понятный гайдлайн для разметки и часть операций проверяем двумя сотрудниками |
| Data leakage | При обучении модель может случайно получить информацию, которая появилась уже после операции | Для признаков используем только данные, доступные на момент операции (feature cutoff) |
| Неправильные labels | Результат работы старых правил может быть ошибочно принят за подтверждённый ответ | Результаты, полученные правилами, используем как weak labels и не считаем их эталонной разметкой (gold) |
| Overblocking | Система может отправить на проверку слишком много нормальных операций | Используем защитные правила (guardrails), пороги и обязательную проверку сотрудником |
| Drift | Со временем поведение клиентов и характер операций могут измениться, и качество модели снизится | Постоянно контролируем изменения признаков, результатов модели и контрольной выборки |
| Vendor lock-in | Сильная зависимость от конкретной ML-модели или поставщика затруднит её замену | Используем единый контракт ScoringService, чтобы модель можно было заменить без изменения остальной системы |
| Правовые и информационные риски | Использование данных или AI-модели может потребовать дополнительных юридических и требований безопасности | До запуска в production проводим проверку Legal и Security |
## План выхода

Чтобы можно было менять ML-модель или поставщика без переделки всей системы, используем единый интерфейс `ScoringService`.

На вход сервис получает операцию, а на выход возвращает:

`operation_id → score, rank, reasons, model_version, timestamp`

Где:
- `operation_id` — идентификатор операции;
- `score` — оценка подозрительности операции;
- `rank` — место операции в очереди на проверку;
- `reasons` — причины, по которым операция получила такую оценку;
- `model_version` — версия используемой модели;
- `timestamp` — время расчёта.

Если появляется новый поставщик или новая модель:

1. Сначала запускаем её в **shadow mode** — она работает параллельно с текущей системой, но не влияет на решения.
2. Проверяем её на том же **наборе тестовых операций (acceptance set)**, что и текущую модель.
3. Сравниваем результаты по заранее определённым критериям.
4. Переключаем систему на новую модель только после успешного прохождения всех проверок.

## Триггеры пересмотра

Архитектуру и выбранный подход нужно пересмотреть, если происходит одно из следующих событий:

| Триггер | Что это означает |
|---|---|
| Запрет размещения | Выбранный вариант размещения модели больше нельзя использовать из-за требований безопасности, законодательства или политики компании |
| Изменение требований к данным | Изменились требования к тому, какие данные можно использовать или как их хранить |
| Нет улучшения качества | Новая модель не даёт заметного улучшения по сравнению с текущим решением |
| Ухудшение guardrails | Защитные правила начинают срабатывать слишком часто или перестают достаточно хорошо защищать систему |
| Появилась качественная разметка | Накопилось достаточно проверенных человеком данных, чтобы перейти к полноценному обучению supervised-модели |
| Изменилась нагрузка на сотрудников | Объём операций изменился настолько, что текущая схема ручной проверки больше не подходит |
| Drift | Характер операций или данные заметно изменились, и качество модели начинает снижаться |
| Существенно изменилась стоимость | Стоимость модели, инфраструктуры или её эксплуатации заметно выросла или снизилась |
